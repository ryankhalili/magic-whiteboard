Four pains we kept hearing about. First, setup: a published higher education case study walks through the plug in, launch, calibrate routine. Second, even after five years with the boards, most instructors in that study used only a fraction of the features. Third, the one we care most about: finding a specific textbook problem live, in front of a class, and the PDF page numbers never match the printed ones. Fourth, cost: the lazy architecture sends the whole board to a large model on every request.

Meet ChalkPal

Your textbook, on the board

Save any PDF to the library. Pull a printed page, or the exact crop of one problem.

Say it or type it

"page 22", "problem 3.2", "exercise 48 in section 5.1", "number 2". Voice or keyboard.

Lands where you need it

Free space ranking puts it in view, with room underneath to work the solution.

Three ideas. One: the textbook lives inside the whiteboard, as a library you import once. Two: you ask for things the way you would ask a TA, by voice or typing. Three: whatever you ask for shows up in a sensible spot, not on top of your notes, with space left underneath to solve it live.

Tested on OpenStax Calculus Volume 1, 769 pages.

This is the core loop. The book has both an Example 3.2 and a Checkpoint 3.2, so instead of guessing, ChalkPal highlights both in the book panel and asks. You say number 2, and the exact crop of that checkpoint lands on the board with work space under it. When there is only one match, like example 3.12, it just inserts it. None of these steps call a large language model.

Top row happens once when you import a book. pdf.js gives us every text line with its position. The printed page numbers come from the headers and footers, because the PDF's own page labels in our test book just count 1 to 769; we vote on the offset between file page and printed number. Then we find anchors: examples, checkpoints, numbered exercises, theorems, including exercises laid out in grids and items that run across a page break. Bottom row happens per request: code builds candidates from exact labels and a BM25 text search, Jev ranks them, pdf.js renders the crop from the vector page, and the placement code finds free space with room below.

Jev: the tiny decider

Jev answers typed questions with calibrated probabilities. It never writes text, so we let it pick, and we let code do the math.

Confident: insert it. Unsure: show the top 3 and let the teacher tap one.

Jev 1.13 by TypeSafe, $0.042 per million input tokens; about 840 input tokens per lookup in our tests.

Jev is a classifier style model: you give it a state and a question, it gives you probabilities over options. It does not generate text, which is exactly what we want for picking which Example 3.2 you meant or which free spot on the board is best. We measured about 0.2 seconds per call and about 840 input tokens per lookup, which at 4.2 cents per million tokens is around four thousandths of a cent. If Jev is confident we insert; if not, we show the top three and let the teacher decide. And the textbook text never goes to the large language model.

Rule we built by: cut the waste, keep every call that makes the answer better.

Measured on our build with the 769 page test book.

Where the money goes. Textbook lookups never touch the large model. A normal typed command with textbook pages on the board sends about three kilobytes of structured board data, with no screenshot and none of the book text. Typing undo does not cost anything. And for voice, our testing caught that every spoken edit was sending the whole board back to the model twice; now it sends a short receipt and the board travels once, in a single replaceable snapshot.

We did not trust our own demo. We indexed a real 769 page calculus textbook, found 3,584 numbered items, and then ran rounds of testing from the teacher's point of view: voice, formulas, cost, PDFs, the canvas, and network failures. Every confirmed problem was fixed and covered by a test. The key files cannot be fetched from the web app, including through encoded paths.
